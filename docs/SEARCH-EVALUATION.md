Две дополнительные связи задокументированы отдельно. [Данные и объяснения к каждой метке](../tests/fixtures/search-evaluation-v1.json)

## Откуда взяты 184 записи

Срез от 24 ноября 2026 года использует локальный кэш публичных наблюдений PortBridge и проверенные ответы GitHub для размеченных записей. Состав по проектам фиксирован: Continued 49, Reforge 38, VIctory 49, XCL 48. Сохранили размеченные записи, включая более старые, и заполнили остальные места по дате обновления отдельно для каждого проекта. В файле есть заголовки и безопасные нормализованные сигналы, доступные для 71 записи. Внешние инструкции, необработанные тела, артефакты и адреса из журналов в набор не входят. [Публичный источник новых наблюдений](https://akimfomin.github.io/PortBridge/data/observations.json)

Запросы зафиксированы после чтения первоисточников. Похожих кандидатов проверили по коду инструкции, ожидаемому поведению или месту сбоя. Для Q06 и Q10 нет проверенных отрицательных меток. Например, похожий результат с полезным обсуждением общей сборки остаётся без метки. Данные не показывают, как часто проекты дублируют работу. Выборка сознательно содержит известные связи и используется для проверки поиска на них. Часть тем есть в публичном каталоге, поэтому это набор для проверки регрессий, а не скрытая независимая выборка.

## Как сравнивать поиск

1. Фиксировать корпус, запросы, `origin_url` и первоисточники до запуска. Для рейтинга использовать только обычные входные данные метода и запрос. Положительные и отрицательные метки читать только на этапе подсчёта. Если проверяем режим с ручными карточками, результат приводим отдельно, потому что некоторые ответы уже присутствуют в карточках.
2. Сравнивать три режима на тех же 184 записях и с одним известным источником. Первый использует только заголовки, второй добавляет технические сигналы, третий учитывает и явные ссылки между проектами. Во всех трёх используется тот же алгоритм ранжирования и тот же фильтр другого проекта.
3. Отдельно сравнивать с публичным GitHub Search по зафиксированной поисковой фразе, с ограничением на три других репозитория. У GitHub больше данных и живой индекс. Это сравнение двух рабочих сценариев: в PortBridge уже известна ссылка на исходную запись, в GitHub вводят короткую фразу. Для GitHub App запросы к Issue и PR выполняются раздельно. Результаты сводятся по месту в каждой из выдач, с сортировкой по ссылке при равенстве. Ошибки и результаты за пределами среза сохраняются отдельно. [REST Search](https://docs.github.com/en/rest/search/search#search-issues-and-pull-requests) · [Search qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests)
4. Главный показатель для задачи перехода между проектами — число запросов, где в первых пяти результатах после исключения известного источника найден подтверждённый материал другой команды. Для одинакового сравнения исключать источник в каждом методе и указывать глубину получения выдачи. Вместе с ним можно сообщать ранг первого найденного подтверждённого источника и сколько проверенных похожих нерелевантных ссылок попало в выдачу.
5. Оставлять остальные результаты без метки. Любой подсчёт доли правильных ответов должен явно приводить число оценённых ссылок, число запросов и покрытие. Ошибка или ограничение GitHub означает пропуск измерения, а не нулевую релевантность. Фиксировать итоговые списки ссылок, чтобы можно было перепроверить расчёт вручную.

Чтобы расширить оценку, следующий человек заранее берёт запросы из новых реальных расследований и размечает объединение результатов двух систем без указания, какая система нашла ссылку. Спорные связи и границы проверки подтверждают участники соответствующих проектов.

## Первый замер

| Метод | Подтверждённая ссылка в первых пяти результатах |
| --- | ---: |
| Только заголовки исходной записи и кандидатов | 6 из 10 |
| Заголовки и технические сигналы | 6 из 10 |
| PortBridge с явными ссылками между проектами | 7 из 10 |
| Публичный GitHub Search по поисковой фразе | 8 из 10 |

Явная ссылка помогла пройти от Continued #15 к Reforge #6. PortBridge пропустил прямоугольники Q01, сборку D3D12 Q06 и инструкцию `ds_bpermute_b32` Q09. GitHub нашёл Q06 и Q09, но пропустил Q01 и сбой при входе Q04. У локального поиска в выдаче было 7 ссылок на весь замер. У GitHub было ещё 12 ссылок без меток. Ни один метод не выдал размеченный неподходящий результат, и этот замер не даёт оценки точности. Набор мал, технические сигналы доступны у 71 из 184 записей. Режим с одними заголовками использует пороги текущего алгоритма PortBridge и показывает вклад признаков в его работу. [Подробные результаты по запросам](SEARCH-RESULTS.json)

Запуск локального сравнения из корня репозитория:

```powershell
python -m portbridge.benchmark tests/fixtures/search-evaluation-v1.json
```

Флаг `--github` включает дополнительный поиск по живому индексу. Повтор может дать другие ссылки или упереться в лимиты GitHub.
