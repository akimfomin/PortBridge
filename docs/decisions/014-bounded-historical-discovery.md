- Проверенный корпус хранит исходники, спецификации, диагностику и обсуждения с исходными состояниями. Запись требует ревизии, лицензии, границ применимости и теста. ## Связи по техническому механизму

В локальном индексе к прежним ссылкам, SHA, техническим словам и идентификаторам добавлены сочетания объекта и операции. Например, blob кэша конвейеров и резервная компиляция, копирование страниц и инвалидирование после смены отображения. Нормализатор оставляет только имена известных сочетаний, найденных в близком контексте заголовка или описания. Для старой записи индекс может извлечь их из сохранённого заголовка. Общий код ошибки сам по себе не даёт ранга точного технического совпадения. Поиск использует списки записей с тем же сочетанием и пропускает слишком частые признаки. Каждая такая связь остаётся кандидатом для ревью. Совпадение полного SHA и прямая ссылка по-прежнему стоят отдельно.

Чтобы повторить, сохраните публичный `data/observations.json` и запишите SHA-256. Запустите следующий код под обеими версиями PortBridge на той же копии.

```python
import json
from pathlib import Path

from portbridge.matching import RelatedIndex, canonical_url

data = json.loads(Path("observations.json").read_bytes())
index = RelatedIndex(data["observations"])
for url in (
    "https://github.com/ubiquitarianism/leonida/pull/1867",
    "https://github.com/LooperSalty/AnyXboxX/pull/476",
):
    own = canonical_url(url)
    ranked = sorted(index.candidates(own), key=lambda row: (-row[1], row[0]))
    print(url, ranked[:5])
```

## Очередь по расписанию

Рабочая очередь хранится в SQLite вместе с позициями и сроками уже известных запросов. В неё попадают открытые наблюдения отслеживаемых репозиториев с извлечённой технической темой. Общие коды сбоя расходуют запрос только при явном поиске, если у наблюдения нет более конкретного сигнала. Повторные темы одной консольной группы делят внешний запрос. Планировщик использует время обновления исходной задачи. Первая сетевая тема в каждом пакете резервируется для самого старого готового запроса. Оставшиеся места получают темы ведущих проектов, обновлённые за последние 24 часа. Свободные места заполняются в порядке ожидания. Готовые ответы из кэша и все задачи выбранной темы используют оставшиеся местные слоты. Это позволяет обработать их без отдельного сетевого запроса. Достигнутый предел или сбой оставляет остаток в очереди. Изменённая ревизия ставится в неё снова. Устаревший внешний ответ не создаёт новый черновик Radar.

Один проход ограничен 5 внешними поисками, попыткой уложиться в 14 секунд и 120 записями для локальной обработки. За один внешний запрос поиск считывает до 15 результатов. Интерактивная выдача показывает до пяти и читает тот же кэш, что и плановая очередь. Публичный снимок по-прежнему отдаёт до 64 недавних источников, а поиск по точной ссылке в локальной базе может обратиться к более раннему результату. Способ восстановления использует существующую публичную копию базы и проходит проверку состава таблиц. Откат — обычный revert к прежнему коду; перед запуском старого валидатора требуется прежняя контрольная копия базы без новой таблицы.

Очередь измеряет число готовых задач, число разных тем и число тем, для которых нужен сетевой ответ. Отдельно видны задачи с готовым кэшем, темп продвижения свежих ведущих источников и возраст старейшей готовой задачи и внешней темы. Отчёт `discovery_scan --online` возвращает эти данные до и после пакета в `queue_metrics`. Возраст отсчитывается от первого помещения в очередь или окончания срока предыдущего ответа. Это измерение работы планировщика, а время с появления исходной задачи проверяется отдельно.

Контрольный повтор использовал ровно один SQLite checkpoint от [плановой публикации 45970589550](https://github.com/akimfomin/PortBridge/actions/runs/45970589550), 33 335 наблюдений, 3 503 готовые задачи, 736 разных тем. Из них 726 требовали сеть, 152 задачи уже имели ответ в кэше. Максимальный возраст готовой темы составлял 4 ч 20 мин 14 с.

В обеих ветках модель использовала 80 удачных внешних запросов, прежние лимиты пакетов и TTL и одинаковый набор исходных данных без новых поступлений. Измеряется скорость обслуживания при доступном GitHub. Реальная задержка расписания и полезность ответов проверяются по наблюдаемым публикациям и источникам. Один пакет с сетевым сбоем или слишком коротким лимитом может выполнить лишь первую старую тему. Новая схема базы не требуется, откат возвращает прежний порядок без миграции.

В отдельном локальном повторе той же контрольной базы с реальными ответами GitHub пять внешних запросов и 115 попаданий в кэш обработали 120 задач. Число готовых задач снизилось с 3 503 до 3 383, сетевых тем с 726 до 721. Это ограниченный эксперимент на копии базы. Основная эксплуатационная очередь не изменялась.
