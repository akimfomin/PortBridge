# PortBridge API v1

[English](API.en.md)

Локальный базовый адрес `http://127.0.0.1:8765/api/v1`. Все запросы используют `GET`. Результаты в Unicode JSON. ID карточки `PB-0001` сохраняется при обновлении статусов и источников.

## Перед началом задачи

```text
GET /api/v1/preflight?q=rectlist&limit=10
GET /api/v1/preflight?url=https%3A%2F%2Fgithub.com%2Fubiquitarianism%2Fleonida%2Fpull%2F207
GET /api/v1/problems/PB-0001
```

`preflight` принимает описание или функцию в `q`, ссылку на Issue, PR или коммит в `url`, либо оба поля. Точный `PB-` ID открывает карточку. По запросу `#772` ответ показывает источники с таким номером в разных репозиториях. У карточек `match_level=confirmed` означает точный ID или проверенный исходный URL. `candidate` обозначает совпадение, которое ещё нужно проверить.

`first_check` появляется при связи исходной задачи с конкретным сравнительным испытанием. Ответ содержит основание `basis`, версию, платформу, результат `outcome` и наблюдение с границами проверки `observed`. Куратор может указать точные исходные ссылки в `check_for`, в том числе для отрицательного результата. Для старого снимка без этого поля доступна прошедшая проверка на прямо связанной реализации. Одинаковый SHA даёт `same_revision`. Отдельно подтверждённая связь двух реализаций может иметь статус `source_port`.

`source_coverage` показывает свежесть получения последних данных, загрузку старой истории и последний проход обновлений по проекту источника. `partial` означает, что проход ещё продолжается. `unavailable` сопровождается причиной сбоя. `unknown` означает, что состояние пока не установлено.

`indexed: false` означает, что текущий снимок ещё не содержит запрошенный источник. Для публичного PR из настроенного репозитория локальную базу можно обновить через `python -m portbridge sync --source <URL>`. При совпадении семейств инструкций `basis: instruction_variants` указывает на материал для сравнения. У него нужно сверить варианты инструкций и границы теста.

## Маршруты

| Путь | Запрос | Ответ |
| --- | --- | --- |
| `/api/v1` | — | Версия, описание и ссылки |
| `/api/v1/activity` | — | Прогресс за семь дней, счётчики команд, события и совместные проверки |
| `/api/v1/lab` | `equipment`, `status` | Очередь для добровольцев с точными версиями, требованиями и ссылками для отчёта |
| `/api/v1/projects` | — | `projects` с `slug`, `repo`, `stack`, `license`, состоянием и свежестью по источникам |
| `/api/v1/problems` | `q`, `project`, `status`, `partial=1`, `limit` | `problems` |
| `/api/v1/problems/{id}` | — | `problem` или 404 |
| `/api/v1/matches` | `q`, `limit` | `matches` с парой источников, статусом и объяснением |
| `/api/v1/related` | `url` публичной задачи, PR или коммита GitHub, `limit` | `indexed` и кандидаты из других проектов для этого источника |
| `/api/v1/observations` | `q`, `project`, `kind`, `limit` | `observations` |
| `/api/v1/preflight` | `q` до 1000 знаков, `url`, `limit` от 1 до 20 | Карточки, кандидаты, тест для первого шага, время синхронизации и ограничения |
| `/api/v1/coordination` | — | Ориентир для сборки и порядок отбора решений |
| `/api/v1/graph` | — | Узлы проектов и карточек, проверенные связи с решениями и зависимостями |
| `/api/v1/source-history` | `url`, `limit` | Зафиксированные смены статуса или ревизии после первого наблюдения источника |
| `/api/v1/recommendations` | `project`, `limit` | Обоснование, уверенность, следующий шаг и тот, кто принимает решение |
| `/api/v1/outreach` | — | `drafts` с предложениями для ручной отправки в открытые обсуждения |
| `/api/v1/health` | — | `status`, `refresh_at`, `observation_count`, `warnings`, прогресс загрузки истории `history` |
| `/feed.xml`, `/feed.ru.xml` | — | Atom проверенного прогресса на английском и русском |

`kind` принимает `issue`, `pr`, `commit`, `test`. `q` ограничен 300 знаками, `limit` от 1 до 200. Недопустимые параметры дают 400, неизвестный путь — 404, методы записи — 405.

### Сводка активности

`window_start` и `as_of` задают семидневный период в UTC. `refreshed_at` показывает время последней попытки обновления. Показатели `health` и состояние синхронизации каждой команды помогают оценить охват данных.

`counts` и `projects[].counts` учитывают фактические слияния по `merged_at`, недавно обновлённые открытые PR, включая черновики, обнаруженные смены статуса или ревизии и датированные проверенные результаты, включая отказы. Один PR может попасть в несколько счётчиков. В `events` до десяти записей каждого вида. В `last_activity` команды может быть событие за пределами этого лимита. В `opportunities` входят открытые задачи, прямо указанные в области применения проверенного теста. У каждой проверки есть ссылка на оригинал.

В `handoffs` собраны подтверждённые вклады PortBridge за всё время. `revision` указывает проверенную версию, а `delivered_url` ведёт в принимающий проект. Ссылки на независимый прогон, ревью и внедрение находятся в `independent_url`, `review_url` и `adopted_url`. Слияние PR на указанной версии учитывается автоматически после обновления индекса. Для другой версии нужно отдельное подтверждение. Счётчики `counts` учитывают только подтверждённые этапы.

## Как читать результаты

- У карточки есть `id`, `status`, `tags`, `platforms`, `dependency_ids` и массив `solutions`. У каждого решения есть статус, источники и подтверждения с точной версией. Пустой `dependency_ids` означает, что куратор пока не зафиксировал зависимость.
- `maintainer_claim` — утверждение автора или участника, который предлагает правку. `automated_test` — исход конкретной автоматической проверки. `independent` — проверка отдельным участником. `source_observation` — наблюдение непосредственно в коде или истории проекта. Читайте `observed` для результата и границ проверки. `verified_count` считает проекты с независимой или автоматической проверкой, включая проверки с отказом.
- `reviewed_same` означает подтверждённую техническую связь. `reviewed_symptom` означает совпадение наблюдаемого симптома с неустановленной общей причиной. `suggested` означает кандидата на проверку. Его `basis` указывает на ссылку из другого проекта, общий технический идентификатор или редкие термины. `score` служит для сортировки. `problem_id` у подсказки отсутствует.
- `outcome` добавляет исход к источнику проверки. Поле `github` рядом с первоисточником содержит отдельно полученный статус PR, задачи или конкретной проверки с датой и ревизией. Слияние PR и результат CI остаются самостоятельными фактами.
- Синхронизированная запись содержит `project`, `kind`, `source_id`, `title`, `url`, `status`, `updated_at`, `fetched_at`, `metadata`. После наблюдения новой версии без SHA поле `metadata.head_sha` пусто, а `metadata.last_known_head_sha` сохраняет последний известный SHA. При получении следующего известного SHA журнал фиксирует смену. У отчёта о тесте остаётся исходный `revision`.
- `seed-only` означает доступный начальный каталог. `partial` означает неполный сбор, `stale` — использование кэша после сбоя, `error` — сбой без данных. `ok` означает успешное получение запрошенных страниц, а не всей истории. У проекта `sources` описывает состояние по типам. Даты в UTC.

## Обмен результатами

`GET /api/v1/outreach` возвращает объект с массивом `drafts`. У черновика есть:

| Поле | Значение |
| --- | --- |
| `id`, `problem_id` | Идентификаторы черновика и связанной карточки |
| `target_project`, `target_url` | Проект и его исходное обсуждение |
| `target_status` | Последний полученный статус обсуждения или `unobserved`, если статус ещё не получен |
| `source_project`, `source_url` | Проект и первоисточник результата |
| `mode` | `reference` для ссылки на существующее решение или `comparison` для сопоставления реализации и наблюдений |
| `message` | Готовый Markdown для ручной проверки и отправки со ссылкой на PortBridge |

Получение и копирование черновиков не отправляет сообщения. Сопровождающий сам выбирает, где уместно обсуждение. У каждой команды остаются её собственные правила приёма изменений. Для сообщения самому PortBridge используется [форма подтверждений в репозитории PortBridge](https://github.com/akimfomin/PortBridge/issues/new?template=evidence.yml).

Отдельный локальный маршрут обмена требует явного включения владельцем и ключей с назначенными правами. Через него доступны временные отметки активной работы, очередь результатов, проверка и упорядоченная выдача принятых записей. [API подключённых агентов](docs/EXCHANGE-API.md)

## Публичный статический режим

По отношению к адресу сайта доступны `data/site.json`, `data/activity.json`, `data/projects.json`, `data/problems.json`, `data/matches.json`, `data/observations.json`, `data/coordination.json`, `data/outreach.json`, `data/health.json`. Форматы данных совпадают с локальным API. Фильтры применяет браузер или агент. `site.generated_at` — время экспорта, `health.refresh_at` — время последней попытки обновления источников. `data/observations.json` содержит накопленные наблюдения. Код и учётные данные не входят в экспорт.

Подписка на `feed.xml` добровольная. В ленту Atom входят карточки с решениями в статусе `verified` или `merged`. У записи стабильный ID карточки, дата фиксации результата в каталоге и ссылка на первоисточник. Точные версии, платформы и происхождение каждой проверки доступны в карточке по её ID. Одна карточка может описывать несколько реализаций с разным охватом проверки.

Для координации также экспортируются `data/graph.json`, `data/source-history.json` и `data/recommendations.json`. Количество зависимостей берётся из проверенных карточек. Изменение результата запуска CI служит поводом для проверки.

Экспорт создаёт отдельную HTML-страницу каждой действующей карточки и перечисляет обе версии в `sitemap.xml`. Для переведённых карточек основной адрес `cases/pb-0001.html` открывает английский текст, а русский доступен на `cases/pb-0001.ru.html`. Исходные поля JSON сохраняются с дополнением `translations.en` для поддерживаемых записей. После отзыва карточки экспорт удаляет обе ранее созданные страницы, сохраняя запись с источниками в архиве.

Агенты могут подключить MCP и вызвать `portbridge_activity` без аргументов. По умолчанию MCP читает публичный снимок. Для своего каталога укажите `--db`. [Подключение MCP](docs/MCP.md)

Очередь Test Lab экспортируется в `data/lab.json`. В `portbridge_lab` можно указать `equipment` со значением `amd`, `nvidia` или `cpu` и отобрать задачи по `status`. Без фильтров доступна вся очередь. В поле `evidence_stage` виден уже выполненный прогон, в `adoption` — решение принимающей команды. [Порядок работы в Test Lab](docs/TEST-LAB.md)
