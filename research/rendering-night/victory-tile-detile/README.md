# VIctory. Detile one changed tile into existing staging

This additive format helper uses the existing row and column address decomposition to update a single 64 KiB physical tile. It applies to a one-mip, one-slice, single-sample, non-tail RGBA8 or BC7 image using one of the two thin non-XOR layouts. It reuses the same column runs for each covered row, limits writes to the corresponding rectangle, and leaves the rest of the initialized staging image unchanged. The ordinary whole detile remains available for every input. The patch targets `940d32f69`. [VIctory #1135 selective detiling](https://github.com/Marvisak/VIctory/pull/1135) · [Exact texture layout source](https://github.com/Marvisak/VIctory/blob/940d32f69b22265690a0b5a15d6ded572ba33baf/crates/victory-formats/src/texture.rs)

Both source comparisons check every possible tile location on four generated images. For each of 160 cases, the result equals the entire full detile, including the unchanged padding in every row. Each invalid control returns without changing the destination. [Current main check](prepared/verified.log) · [Check against #2026](prepared/verified-vs-2026.log)

## CPU preparation times

The candidate has two arms. The first copies the one tile only. The second also byte-compares the old and new snapshots outside the tile before writing. Each displayed arm is a median over 48 trials, from four fresh processes and eight trials of each of the six orders. The reported allocations and test checks outside the measured subroutine are the same per shape. The CPU subroutine assumes the snapshots and existing staging are already in memory. This measures neither snapshot acquisition nor runtime upload. [All samples](prepared/cpu-summary.json)

| 512×512 RGBA8 S | 71.70 µs | 63.75 µs | 4.40 µs | 40.20 µs |
| 1024×1024 RGBA8 D | 372.50 µs | 320.00 µs | 7.10 µs | 279.55 µs |

The last two columns use the matched trials against 0xkn0wh3r3's [#2026](https://github.com/Marvisak/VIctory/pull/2026) at `376946af`. The outside check remains a large part of the CPU cost. The patch uses the current main's private run helper. A combined implementation on #2026 would adapt it to that PR's refactored signature before the usual integration checks. ## Reproduce

Save each linked `texture.rs` byte-for-byte. Use Rust edition 2024 and an appropriate Windows linker. The check uses source-generated bytes and no device. `prepare.py` checks the pinned main file and generates the earlier and candidate source.

```powershell
python -I -B .\prepare.py .\texture-main.rs
rustc --edition 2024 -C opt-level=3 -A dead_code -D warnings .\check.rs -o .\prepared\check.exe
.\prepared\check.exe --check
.\prepared\check.exe --time > .\prepared\cpu-a.csv
```

For the #2026 comparison save its exact full source to `prepared/full_2026.rs` (SHA-256 `777e3d3f2b8c24d334769f811c92c43cae2632716ccd3c54afb8d6310581b5ab`), add `--cfg use_2026` to the compiler command, and redirect the timing output to `prepared/next-a.csv`. The analyzer reads the `cpu-*.csv` and `next-*.csv` files. [Exact #2026 source](https://github.com/Marvisak/VIctory/blob/376946afab72a060004096c0d50bb14667e2c121/crates/victory-formats/src/texture.rs)
