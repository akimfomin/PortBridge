# Exact-name admission review · `c96b4f2b`

## Call and lock order

The three direct call sites are compute (`LoadComputePipeline` / `CreateComputePipelineState`), ordinary graphics (`LoadGraphicsPipeline` / `CreateGraphicsPipelineState`), and shared PSO-stream handling (`LoadPipeline` / `CreatePipelineState`). Depth-bounds graphics and mesh feed the shared stream function. Graphics fallback reaches its second call after the previous one returned. The load and create closures at these sites terminate in D3D12 interface methods and have no project callback into `library::pipeline`. The project opens the pipeline library before acquiring admission, and returns the PSO before per-object naming or error logging in its callers. [Compute](https://github.com/fxceless/victory-fork/blob/c96b4f2b8365bf43d54ab074940923ef8267f4c6/crates/victory-gpu/src/pipeline/host.rs#L525-L548) · [Graphics](https://github.com/fxceless/victory-fork/blob/c96b4f2b8365bf43d54ab074940923ef8267f4c6/crates/victory-gpu/src/pipeline/host.rs#L661-L699) · [Stream callers](https://github.com/fxceless/victory-fork/blob/c96b4f2b8365bf43d54ab074940923ef8267f4c6/crates/victory-gpu/src/pipeline/host.rs#L761-L896)

- Name admission waits with the map mutex released. Its lease spans load and conditional create/store. The map mutex itself covers only map accesses. On exit, the lease releases the name after any local driver-call tracking and store guards have been released, then signals the old waiters.
- Load may take the optional `one_call` mutex. Create takes neither `one_call` nor `saving`. Store takes `one_call` then `saving.read()`. Save takes `one_call` then `saving.write()` and never acquires a name lease. The periodic save runs after `Pending::make()` returns. Trimming also never acquires a lease.
- `CALLS` and `TRAIL` acquire local logging mutexes only to update state. `CALLS` drops its lock before returning the tracer guard. The `TRAIL` formatter runs before taking its lock. Their inspected call paths have no reverse dependency on name admission. This review covers repository code and the documented API boundary. [Library](https://github.com/fxceless/victory-fork/blob/c96b4f2b8365bf43d54ab074940923ef8267f4c6/crates/victory-gpu/src/pipeline/library.rs#L512-L612) · [Worker save order](https://github.com/fxceless/victory-fork/blob/c96b4f2b8365bf43d54ab074940923ef8267f4c6/crates/victory-gpu/src/pipeline/make.rs#L312-L318) · [D3D12 thread safety](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device1-createpipelinelibrary#thread-safety)

A long save can still delay publication while the first caller waits to store. Same-name followers then wait for that publication. This design trades duplicate driver work for waiting on the first caller when the name overlaps. A store refusal or a different descriptor can still make a later create necessary.

## Warm control

The existing harness primes one 32-byte synthetic host name and the map capacity. A thread-local forwarding allocator then counts allocations across 12 uncontended warm calls through each extracted `pipeline()`; it counts no GPU or driver memory. The baseline requested 12 allocations and 384 bytes, all from the harness string stand-in for the Windows name. V2 requested 24 allocations and 768 bytes. The difference is exactly one 32-byte copy per warm call from inserting the owned map key. No waiter allocation occurs in those calls. Each arm passed 6/6 with the diagnostic global lock off and on. This measures allocation count and requested bytes. It does not measure warm-path time. A typed inline key could remove the extra copy if subsequent measurements justify changing the name API. ## Aggregate check for #470

KretliJ's original #470 report offers to log extra counters. The public issue was open with zero comments when checked. The existing `being made` number includes both queued requests and active worker jobs. Its steady value alone cannot distinguish them. [KretliJ's report](https://github.com/fxceless/victory-fork/issues/470) · [Queue accounting](https://github.com/fxceless/victory-fork/blob/c96b4f2b8365bf43d54ab074940923ef8267f4c6/crates/victory-gpu/src/pipeline/make.rs#L106-L113)

Count total host creates and starts where another create for the same name is already active, using a temporary per-name count around the original `create()` with cleanup on return or error. Record peak concurrent same-name creates, cache hits/misses and successful/refused stores in an early and a later stable window. Export only the aggregate totals and revision. Names and other workload data can stay local. An overlap is a same-key signal. D3D12 also checks the descriptor on load, so an overlap alone is not proof the two calls had matching descriptors. If strong overlap persists later, repeat with the candidate under equivalent cache conditions. A near-zero overlap in the later window would deprioritize this mechanism for that backlog.

## Independent cold and settled measurements

KretliJ measured the same area from an empty pipeline library through a later settled interval on `2119b0e`. He implemented the per-name in-flight count suggested in review, then published his instrumentation under the fork's GPL-3.0-or-later license. Use his original Gist for the patch. [Author's patch and permission to link](https://github.com/fxceless/victory-fork/issues/470#issuecomment-7152294339) · [KretliJ's patch Gist](https://gist.github.com/KretliJ/14f6d8988467df07cba62f29890ee0ae)

In his first interval, 10 of 1,742 starts overlapped another creation of the same name and 11 stores were refused. The backlog later drained to zero with no overlaps across four new creates. This confirms that overlap occurs and makes it a low-priority explanation for that run's sustained frame cost. This was an instrumented observation, without a separate baseline/candidate frame comparison of the PortBridge admission change.
