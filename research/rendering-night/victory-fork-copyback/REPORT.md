## What the frame counters measure

With relay enabled on reported `2119b0e`, `relay_wait()` charges the caller's wait for flights to finish landing to the number printed as “on the GPU”. `relay_land()` charges its work through CPU shadow merge and completion bookkeeping to “copying back”, including its own fetch command recording and fence wait on the DIRECT queue. A caller can be waiting inside the first number while the worker is accumulating the second. A single landing may also run in parallel with preparation or unrelated queue work. `Meter` divides each separately accumulated counter by the number of presented frames in the sampling window. The original report enabled `RELAY=2`; the stable-window comment names two other flags and does not restate relay. Check for the “the relay per frame” line from that same window before applying this relay interpretation to its 464/482 ms. `2119b0e` needs explicit relay opt-in, while live `310c6eb` turns it on by default. ## A measurable source-level redundancy

For both pins, `relay_card_back()` records one `CopyBufferRegion` per logical 64 KiB clipped piece after exact duplicate filtering. Consecutive commands can read adjacent portions of one buffer, or different portions that overlap. The source trial packs only consecutive commands in forward order for the same `Shadow`, with no read across a gap and a 1 MiB cap on joined commands. Each logical merge piece retains an offset into the packed buffer. It then receives its original bytes and arrives in its original order. Queue selection, fence wait, dirty exclusions, `card_merge_relay()`, and the number of fetch submissions stay on the original path. [Pinned readback](https://github.com/fxceless/victory-fork/blob/310c6eb6c16822ab95076aad61fce19bba86bb98/crates/victory-gpu/src/host.rs#L3347-L3458) · [Pinned merge](https://github.com/fxceless/victory-fork/blob/310c6eb6c16822ab95076aad61fce19bba86bb98/crates/victory-gpu/src/shadow.rs#L2691-L2753) · [D3D12 buffer-copy API](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-copybufferregion)

| Synthetic sequence | Original commands | Packed commands | Original → packed bytes |
| --- | ---: | ---: | ---: |
| One 1 MiB run in 64 KiB pieces | 16 | 1 | 1,024 → 1,024 KiB |
| Two overlapping clips and one adjacent piece | 3 | 1 | 112 → 96 KiB |
| Sixteen sparse pieces separated by gaps | 16 | 16 | 1,024 → 1,024 KiB |

The Python byte oracle passed five checks, including 250 randomized sequences. Each logical piece was compared byte for byte against an independent slice of its original source. The Rust change passes `git apply --check --whitespace=error-all` on both pins. The Rust crate, D3D12 queue and performance are unverified. The source trial is off by default. `VICTORY_RELAY_PACK_FETCH=1` enables it and adds one aggregate line for requested and recorded commands and bytes. A low reduction in recorded commands or a fetch wall time dominated by waiting behind other queue work would make this experiment low-value.

## Current upstream work and next measurement

#71 already combines a dedicated COPY queue and parallel card comparison. Its RTX 3080 A/B reports 121.4 ms/frame down to 6.8–7.0 ms for the fetch-wait counter, with different observed fetched byte totals. These are the author's bundled results. Our candidate changes only read command packing within the existing queue and needs same-queue A/B. #255 targets CPU first/last-difference scans. #496 covers reupload after a waited fetch. A receiver can use the source-generated `#651` benchmark if its released fixture drives relay fetches, or choose a small source-generated workload with a dense positive control and sparse negative control. [#71 queue and compare](https://github.com/fxceless/victory-fork/pull/71) · [#255 CPU scans](https://github.com/fxceless/victory-fork/pull/255) · [#496 upload path](https://github.com/fxceless/victory-fork/pull/496) · [#651 synthetic benchmark](https://github.com/fxceless/victory-fork/pull/651)

First establish whether the receiver's stable windows have a large fetch component with the existing diagnostics. For an isolated synthetic A/B, keep queue and flags fixed, use identical source and payload changes, require byte-identical results, and record command count, bytes, command recording time and the fence wait independently. Check both sparse and dense sequences, and represent the phase timeline as paired samples. This would distinguish packing overhead from direct-queue waiting and memory transfer. Any changes to queue ownership belong to a separately reviewed experiment.
