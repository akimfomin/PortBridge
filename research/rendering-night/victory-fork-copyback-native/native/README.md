# Bounded D3D12 readback copy A/B

This fixture uses the exact local Rust packer from the victory-fork relay patch. A C++ probe runs its output against the per-piece baseline on one DIRECT queue. Both arms receive the same original generated buffer, and each timed arm writes to a fresh destination window. The dense and sparse cases transfer exactly the same number of bytes across arms. In the overlap case the packed arm skips duplicate physical transfers while preserving every original logical read. [Fork case and pinned source](../README.md) · [D3D12 buffer-copy API](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-copybufferregion)

| Case | Baseline commands and bytes | Packed commands and bytes |
| --- | ---: | ---: |
| Dense | 16, 1,048,576 | 1, 1,048,576 |
| Overlap | 3, 114,688 | 1, 98,304 |
| Sparse | 16, 1,048,576 | 16, 1,048,576 |

For each case, the first pair warms the path and is verified without participating in the summary. The eight measured pairs alternate arm order. Destination offsets cross over independently. Process `b` reverses case order and initial arm order and uses a different deterministic source pattern. Every logical region is compared byte for byte and the rest of each output window is checked against its initialized guard pattern. The CPU duration brackets only the API recording loop, excluding layout generation, initialization, submission and fence. GPU timestamps bracket only the timed copies and are scaled by the queue frequency. These are local synthetic measurements. They do not predict a title's frame time or how long a fetch waits behind unrelated work. [D3D12 timestamps](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing)

The probe uses a fixed RTX 4070 Ti SUPER, 512 MiB job cap and three-second guard. The guard requires 4 GiB free system commit and 6 GiB available physical memory for the child admission. The child checks again before opening a device. No source input, launch arguments, settings or driver edits are needed. Every buffer is generated by the fixture.

```powershell
.\build.ps1 -Rustc rustc -Compiler clang++ -OutputDirectory .\proof-a
.\proof-a\relay-readback.exe --hardware-a > .\proof-a\result-a.csv
.\proof-a\relay-readback.exe --hardware-b > .\proof-a\result-b.csv
python .\analyze.py .\proof-a\result-a.csv .\proof-a\result-b.csv
```

Build and hardware trials are separate. The build compiles the exact Rust planner and static case validator, then exercises `--cpu` without opening a device. Hardware slots run one child at a time and stop on the first refusal or verification error. The original guard is MIT and the synthetic relay sources are GPL-3.0-or-later.

## Local CPU checkpoint

The reviewed planner hash and worker guard matched. Rust and C++ compiled with warnings denied, and the no-device self-check reported three cases and 54 distinct windows totaling 56,650,752 bytes. The result parser also accepted both synthetic crossover schedules and rejected an intentionally reused destination window. [Build log](build-a.log) · [Exact generated plans](proof-a/relay-cases.inc)

For the scheduled hardware campaign, `run_ab.ps1` checks the worker digest and records fresh admission values before each polarity. The trial does not exercise multiple D3D12 queues, title-memory ownership, or background queue contention. The fork's existing piece count can still refer to logical pieces after packing, so the new fixture explicitly counts the physical commands and bytes separately.

## RTX 4070 Ti SUPER result

Both fresh workers completed and were reaped. Each verified all 54 output windows, totaling 56,650,752 bytes per process with the untouched padding included. The queue reported a 1 GHz timestamp frequency. Peak job commit was 167,333,888 and 162,840,576 bytes. [Run A](rtx-ab/result-a.csv) · [Run B](rtx-ab/result-b.csv) · [Admission A](rtx-ab/preflight-a.json) · [Admission B](rtx-ab/preflight-b.json)

| Case | CPU recording median, baseline → packed | GPU median, baseline → packed | GPU paired median saving |
| --- | ---: | ---: | ---: |
| Dense, equal 1 MiB | 4.20 → 0.30 µs | 55.472 → 54.496 µs | 0.608 µs |
| Overlap, 112 → 96 KiB | 0.80 → 0.30 µs | 5.280 → 4.352 µs | 0.944 µs |
| Sparse, equal 1 MiB | 4.20 → 4.20 µs | 57.488 → 57.168 µs | 0.080 µs |

The packed dense arm was faster to record in all 16 measured pairs. Its GPU result was small beside the spread of the unchanged sparse control. The overlap arm was faster on both counters in all 16 pairs and copied fewer physical bytes. The CPU timings exclude plan construction and the additional work of integrating the plan in the fork. The run retains the sparse 925.472 µs baseline and 540.768 µs packed intervals. It does not establish that packing will materially change frame time.
