# AnyXboxX disk-cache pressure

Base: AnyXboxX `b10149942d972ed2b1d7b721cce63347f086a0f8`. The cache owner is LooperSalty. Their original work reports 21.6 ms for DXC and 1.4 ms for a disk hit. Those timings describe normal lookups. This experiment exercises insertion into an already full disk cache. [Cache goal and measurements](https://github.com/LooperSalty/AnyXboxX/issues/25#issuecomment-7067942768) · [Original optimization](https://github.com/LooperSalty/AnyXboxX/pull/58)

The base reads every record's modification time for sorting, reads every size for the total, and reads evicted sizes again. The patch takes one fresh metadata snapshot during a prune. A heap selects the oldest entries in order, with the existing directory traversal order breaking equal timestamps. The first write also sizes the existing cache without sorting it. Eviction stops at the configured capacity. Each prune still scans the cache linearly. [Base code](https://github.com/LooperSalty/AnyXboxX/blob/b10149942d972ed2b1d7b721cce63347f086a0f8/PrototypeScarlett/emu/shader_cache.py#L81-L110) · [Python heap construction](https://docs.python.org/3.12/library/heapq.html#heapq.heapify)

## CPU-only proof

The script creates all files in temporary directories. Each record is 4 KiB of generated bytes with the cache's required header. It fills a 256 KiB cache with 64 old entries, puts 64 more through the ordinary method, and checks exact capacity and survivors after each write. It counts calls at the Python path API.

```powershell
python proof/cache-pressure.py --source ../unchanged-b1014994-checkout
python proof/cache-pressure.py
$env:ANYXBOXX_DXC = Join-Path (Get-Location) 'proof/no-dxc.exe'
python -m pytest -q tests/test_shader_cache.py tests/test_readme_sync.py
```

During the 64 writes at capacity, metadata calls fell from **8,448 to 4,224**. Full directory scans were **64 on each version**.

A serialized Windows comparison alternated the order of six paired samples, each with 16 writes at capacity. The median at 64 resident records was **3.3167 → 3.0575 ms per put**. At 256 it was **3.6474 → 2.7879 ms**. Both figures use 4 KiB records in a temporary directory, not a game's workload.

A separate process opened a disk hit and refreshed the file's modification time, and both versions retained it. A RAM hit left that timestamp alone. The pytest regression also covers equal timestamps and an unrelated file in the cache directory. The evidence records invalid input rejection, corrupt file cleanup, and oversized input behavior.

Each writer still keeps its own total. In a separate two-process control, both versions reached 12 KiB on disk with an 8 KiB configured capacity when one writer's running total missed a second writer's insertion. The patch's capacity and exact eviction controls cover ordinary single-writer use, including disk reads from another process.

## Scandir experiment

The alternative uses the metadata from Windows directory enumeration. It saved time in the test and matched normal suffixes, uppercase and Unicode suffixes, absolute and relative paths, directories named with the suffix, and real file/directory symlinks. It returned the old size for an already deleted regular file, where fresh `Path.stat` raised `FileNotFoundError`. The candidate keeps fresh path stat behavior. [Python directory-entry metadata](https://docs.python.org/3.12/library/os.html#os.DirEntry.stat)
