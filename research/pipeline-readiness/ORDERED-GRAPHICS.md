# Ordered recording across cold graphics builds

## Why XCL waited

The follow-up to the 162-second RTX 5070 Ti trace identifies one specific priority inversion. The two-pass mesh builder reserved a heavyweight creation slot using the sum of a cold 34,956-byte mesh shader and a 164,772-byte compute partner. The mesh alone was below the run's 65,536-byte threshold and the driver accepted the partner's cached blob. In the reported baseline, 26.143 s of the 26.359 s consumer wait elapsed before entry to the driver. The author's per-pass admission changed that consumer wait to 0.447 s with zero admission delay. The combined-gate source acquires the slot before looking up the partner's blob. [Updated XCL trace](https://github.com/xcl-dev/xcl/issues/2088#issuecomment-7172696323) · [Source at 6d12f58](https://github.com/xcl-dev/xcl/blob/6d12f58a229bc73889878a448c64dc3af25eeba0/crates/xcl/src/hle/d3d12x/real.rs#L5917-L5968)

This isolates one wait on the critical recorder. The same report measured two later improvements from 164.23 to 19.87 s and from 76.36 to 6.41 s. Those runs also changed scheduling, cache state and the base revision. A phase breakdown for the other required keys and a verified visible frame remain unavailable. A separate RX 9070 XT report measured 36–113 s within several individual cold native calls on an older revision. That is evidence of a second mechanism on a different system. [NVIDIA observation](https://github.com/xcl-dev/xcl/issues/2088#issuecomment-7172696323) · [AMD observation](https://github.com/xcl-dev/xcl/issues/2088#issuecomment-7173444000)

The per-pass improvement belongs to its XCL contributor. It can keep an unrelated cached pass from delaying a cold pass. A recorder still serializes across first use when the next required graphics recipe is discovered only after the previous wait. XCL #2118 moves some compute waits to submission but retains that graphics wait. XCL's journal can replay exact descriptors that already exist, with coverage limits for guest mesh stages. [Current indirect bind](https://github.com/xcl-dev/xcl/blob/6d12f58a229bc73889878a448c64dc3af25eeba0/crates/xcl/src/hle/d3d12x/bind.rs#L269-L279) · [Descriptor replay](https://github.com/xcl-dev/xcl/pull/759)

## Implementation

The [ordered recorder](ordered_graphics.hpp) queues native builds when actual draw packets reveal their exact recipes. A bounded window owns copies of draw arguments and keeps discovering subsequent draws while builds are in progress. Playback waits for each recipe before binding and emits draw packets in their original order. It flushes at the capacity limit and at the end of the compatible block. One queue entry can serve repeated keys. Compilation errors permanently stop that window and abort frame submission. The code has no prior-run input.

The [Vulkan integration](full-scene/scene.cpp) uses a compatible render pass scope with common attachments, index and vertex buffers, and descriptor layout. It keeps the resources live through fence and readback. The call to create a native pipeline runs on up to two workers. The same Vulkan cache is created without the externally synchronized flag, so the driver owns its synchronization. Native API intervals show concurrency of calls as observed by the application. They do not expose the driver's internal compiler scheduling. [Vulkan pipeline creation](https://docs.vulkan.org/refpages/latest/refpages/source/vkCreateGraphicsPipelines.html) · [Vulkan pipeline cache flags](https://docs.vulkan.org/refpages/latest/refpages/source/VkPipelineCacheCreateFlagBits.html)

An XCL port needs an ownership boundary for pipeline, indirect and count buffers, stable descriptor data, and the original graphics binding state. It must flush before any operation whose dependencies or side effects it cannot represent. In particular, descriptor addresses alone do not preserve the graphics state captured by an earlier API call, and a reset establishes a new recording generation. For initial integration, scoped direct draws or DRAW/DRAW_INDEXED-only indirect signatures with stable state offer a narrower contract than predication, root-changing indirect arguments, mesh emulation, or arbitrary command list splitting. The compute-only XCL replay restores descriptor heaps after reset. Extending its eligibility alone would record graphics commands with missing state. [XCL replay source](https://github.com/xcl-dev/xcl/blob/6d12f58a229bc73889878a448c64dc3af25eeba0/crates/xcl/src/hle/d3d12x/list_x.rs#L2680-L2715) · [D3D12 recording and ownership](https://learn.microsoft.com/en-us/windows/win32/direct3d12/recording-command-lists-and-bundles) · [D3D12 indirect drawing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/indirect-drawing)

## Open workload and controls

The native Vulkan runner renders three views of the open ASWF scene *A Beautiful Game*, using all 49 indexed draws, 1,500,224 instantiated triangles, 15 materials and the scene textures per output. The first view uses exact material-specific pipeline recipes derived from texture bindings, base color and opacity. The other two views add four diagnostic recipes. The shader's authored disk light integrates 192 deterministic quadrature points using a GGX material calculation. The expanded form makes shader size and cold creation costly while lighting actual scene geometry. The compact loop is available independently to test sensitivity to shader representation. The asset, lighting and bytecode differ from XCL's workload. The experiment targets native creation for a comparable **number** of first-use keys, with fully permitted inputs. [Scene and license](full-scene/README.md#source-and-attribution) · [glTF material reference](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#appendix-b-brdf-implementation)

All arms create the same logical recipes and issue the same draws. The first-use blocking arm represents the serial graphics recorder. The ordered arm discovers keys from live packets. The eager arm walks the exact packet order and gets the frame's required keys into the compiler queue before recording, a baseline with the information needed for optimal lookahead in this test. A prior compatible cache can still do more than either cold strategy. An isolated giant native call and driver-enforced serialization can also limit the gain.

The runner alternates order, records distinct shader digests and checks compile-required status for every key before timing. Each run verifies six or nineteen native creates, depending on the workload. For the large material scene it also counts all real draws in each frame and compares the complete three images byte for byte across arms. Fresh identifiers and feedback make an exact application-cache hit detectable. Driver-managed partial reuse remains possible. Startup and recording both have measured endpoints. Peak private memory comes from Windows' process high-water counter. The heavy process is capped at 1.5 GiB of private commit and begins only with at least 5 GiB system commit headroom and 6 GiB available physical memory. The runner enforces a 45-second deadline for each process. [Windows job limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)

## RTX 4070 Ti SUPER results

Six blocks on Windows, NVIDIA driver 617.14, cover each of the six possible orders of the three arms. Every arm in the primary comparison uses a 362,556-byte fragment module with an independent salt. The timing unit is the complete renderer operation through synchronized image readback. All 54 images matched their corresponding reference hashes. All 342 native creates had the expected compile-required preflight and valid feedback without an application-cache hit.

| Median of six runs | Blocking first use | Ordered discovery | Eager known keys |
| --- | ---: | ---: | ---: |
| Recording start to first checked image | 11.983 s | 6.306 s | 6.257 s |
| Recording start to all three checked images | 12.164 s | 6.439 s | 6.390 s |
| Process startup to first checked image | 12.252 s | 6.598 s | 6.523 s |
| Process peak private commit | 279 MiB | 336 MiB | 356 MiB |

Ordered discovery beat blocking first use in all six pairs. Its median paired first-image gain was **5.571 s**, with individual gains from 3.355 to 5.915 s. From process start the median latency fell 46%. The difference between ordered and eager was small relative to the cold workload, and eagerness remains the stronger choice when exact demands are already available. Native calls overlapped for 5.36–6.00 s before the first image in the ordered arm and never overlapped in the blocking arm. The longest observed individual first-frame create was 1.056 s. The measured improvement came from overlapping many required creates. This workload does not establish the same effect during a single minute-long native call or on XCL's full dependency chain. [Confirmation runs](full-scene/evidence/ordered-graphics-575.jsonl) · [Summary](full-scene/evidence/ordered-graphics-575.json)

In a separate three-run compact-loop control, the fragment module was 9,072 bytes. Recording to first image was 0.374 s blocking, 0.211 s ordered and 0.213 s eager. Within those arms all nine images were identical. Across the two shader representations one pixel in the first view differed by one channel unit and both diagnostic views matched. The large change in absolute timing shows the scheduling result depends on the existence of many expensive builds. When developers can change the shader source, a compact representation can offer a larger benefit on this workload and requires its own correctness check. ## Reproduce

Use the existing Windows native Vulkan build and asset preparation instructions. Run the first command from `research/pipeline-readiness/full-scene` with the locally prepared input and compiler tool paths. Choose a new output folder and campaign identifier on later runs.

```powershell
python -B run.py run results-575 --executable build-574/scene.exe --scene-dir prepared --dxc $dxc --validator $spirvVal --adapter 'NVIDIA GeForce RTX 4070 Ti SUPER' --campaign 575 --groups 6 --record --area-nodes 192 --material-recipes
& $clang -std=c++20 -O2 -Wall -Wextra -Werror -static ../test_ordered_graphics.cpp -o ordered_graphics_test.exe
./ordered_graphics_test.exe
```
