# Graphics builds on the first-output path

## Measured bottleneck

On Windows with an RTX 5070 Ti, warmed compute pipelines and XCL `06055a7` plus local scheduling changes, a public run recorded a presenter waiting on a guest semaphore from **118.619 s to 280.832 s**. The recording thread that could release it spent **162.01 s of those 162.213 s** in the union of graphics pipeline resolution intervals for the same command list. That run recorded 19 distinct logical keys, 17 through graphics `ExecuteIndirect` and two through `DispatchMesh`. About 65 ms elapsed from the signal to batch submission. There were no presents during the wait. The run did not establish when a correct visible world frame arrived, and the public table does not split those 162 seconds by compilation phase. This is one externally reported run on its stated revision. [XCL causal trace](https://github.com/xcl-dev/xcl/issues/2088#issuecomment-7172696323)

XCL #2118 moves an eligible pending **compute** dispatch's wait to submission. The source after that merge and #2368 still waits in the recording path for graphics `ExecuteIndirect` and normal draws. The resolver may run the build on the caller or wait on a condition variable until another thread finishes it. #2368 lowers the cost of some compute programs but preserves the existing graphics lowering after a synthetic pixel case regressed from 1.632 to 9.203 s. The remaining bottleneck is a required, cold graphics pipeline on a recorder that gates forward progress. The 162 seconds quantify the aggregate wait on that dependency. A fresh paired run would be needed to quantify it on merged main. ## What existing techniques cover

| Technique | Evidence and remaining limit |
| --- | --- |
| Demand priority and compute deferral | Existing scheduling changes can make room for required work or move a recording wait. The native build of a required, cold graphics key still has to finish before its work runs. [XCL #1996](https://github.com/xcl-dev/xcl/pull/1996) · [XCL #2118](https://github.com/xcl-dev/xcl/pull/2118) |
| Earlier compilation from a journal or a cache | The #755 stack can journal complete queued descriptors and replay eligible entries across runs or alongside recording. It currently excludes guest GS/HS/DS/mesh. A separate VS/PS prototype shifted 459 summed in-run driver seconds to 0.8 s after an external precompile that itself took 263 s. The report timed device removal and did not establish time to correct output. A first-seen recipe can only be scheduled once its complete identity is available. [XCL #755](https://github.com/xcl-dev/xcl/issues/755) · [Replay prototype report](https://github.com/xcl-dev/xcl/pull/759#issuecomment-7157739982) · [D3D12 cache compatibility](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_cached_pipeline_state) |
| Lower compilation cost | Five isolated cold RTX 5090 pixel cases in #2446 took 8.597–10.948 s before its change and 8.466–10.851 s after it. The sum of medians fell 5.3% and two cases regressed. #2438 measures native creation in isolation. TuxBox #141 reduces DXC time by 0.083–0.215 s on three large synthetic pixel cases and checks output separately. Translation and native pipeline creation need separate timings on the same critical path. [XCL #2446](https://github.com/xcl-dev/xcl/pull/2446) · [XCL #2438](https://github.com/xcl-dev/xcl/pull/2438) · [TuxBox #141](https://github.com/brcly/TuxBox/pull/141) |
| Skip a pending draw or draw with a stand-in | This can advance a preview. A correct-output comparison still requires the original work. [XCL #1798](https://github.com/xcl-dev/xcl/pull/1798) |

Godot #111129 is an existing comparison for overlapping known pipeline builds with other loading work. One RX 6900 XT report measured initial load at 19 s or 27 s, depending on the driver, and 3 s after the change. The PR also documents that releasing a shader can still wait on background compilation. That makes full load and completion times pertinent alongside first output. [Godot observation](https://github.com/godotengine/godot/issues/112425) · [Merged implementation](https://github.com/godotengine/godot/pull/111129)

This narrows the Cold Pipeline Readiness question to **what delays required graphics keys that were unavailable to useful warmup**. A trace must establish when each complete recipe became usable and whether work with that identity was queued, in translation, waiting for a native slot, or executing the native create call. If a recipe was available ahead of demand, start with measured admission and replay. If an isolated native call still dominates with little head start, reducing its cost is the more direct lever. A change that simply moves the same wait outside the timed scope needs a first-launch comparison with prebuild time included.

## Inspect a sanitized trace

```powershell
python -B research/pipeline-readiness/heavy_wait.py research/pipeline-readiness/evidence/heavy-wait-synthetic.json
python -B -m unittest discover -s research/pipeline-readiness -v
```

The input is one JSON object with a `wait` and a `resolutions` array. Each interval uses half-open `begin_us` and `end_us` timestamps on the same monotonic clock. The wait's `producer` and `command_list` identify the recorder and the generation of the list shown to release that particular wait. Export only actual blocking graphics resolves for that pair. Use a fresh list identifier after each reset. Each resolve carries its own `pipeline` key and may carry `phases` with `kind`, `begin_us` and `end_us`. No shader bytes, descriptors, addresses or application data are needed in the exported file.

The producer of the trace establishes the dependency and uses an opaque identity for the full logical pipeline recipe. Shader hashes alone can alias pipelines with different render-target formats, fixed-function state or root signatures. Attach a phase only to the exact build attempt on which that resolution is blocked. Clip earlier in-flight work and later spans at the resolve's boundaries before export. Record an outer admission wait once even when a logical mesh pipeline issues two native calls and retries one of them. The XCL two-pass path acquires a single outer slot before the graphics call, performs the compute call separately and installs both together. [D3D12 pipeline description](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_graphics_pipeline_state_desc) · [Two-pass admission](https://github.com/xcl-dev/xcl/blob/6d12f58a229bc73889878a448c64dc3af25eeba0/crates/xcl/src/hle/d3d12x/real.rs#L5917-L5929) · [Two-pass completion](https://github.com/xcl-dev/xcl/blob/6d12f58a229bc73889878a448c64dc3af25eeba0/crates/xcl/src/hle/d3d12x/real.rs#L5951-L5987)

- `build_queue` is time queued for a pipeline build. `translation` is time spent translating or producing the host shader. `driver_admission` is time waiting to be allowed to start native creation. `native_driver` is time inside native pipeline creation, including recorded retries.
- The report partitions elapsed time within the selected wait. Each reported phase duration is the exclusive, fully covered portion. It counts concurrent spans with the same phase once, reports different overlapping phases separately, and leaves gaps in matched resolves unattributed. Time outside the provided resolves can include missing data or other work. A zero phase duration can mean the trace contains no usable timing for that phase. Repeated resolutions of a key count once toward distinct keys and can each contribute elapsed time.
- The synthetic 160-second example confirms the accounting with an unrelated background build, overlapping phases, and missing spans. It is not a recreation of the public XCL run and supplies no measured speedup.

On the next measured run, capture exact recipe availability, matched phase intervals, release signal, batch submission, first checked image and peak process commit. Compare against current demand-first scheduling and exact cached replay when available. Use the same required keys and validate output under both policies. Observed late request timestamps already include earlier delays, so summing per-key speculative savings would overcount the available overlap. The public 162-second observation remains unattributed within pipeline resolution until complete timings on that dependency are available.
